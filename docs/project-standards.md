# Правила и стандарты проекта

Статус: accepted, обязательный стандарт проекта, версия 1.2.
Дата: 2026-08-30

Документ определяет правила разработки, тестирования, документирования и принятия решений для тренировочной биржи.

## 1. Базовые принципы

- Сначала фиксируются требования и инварианты, затем пишется код.
- Доменная логика не зависит от NestJS, PostgreSQL, Redpanda, HTTP и WebSocket.
- Состояние и денежные операции изменяются только через явно описанные команды и события.
- Любое решение, влияющее на архитектуру, данные, безопасность, производительность или публичный контракт, должно быть задокументировано.
- Простота важнее преждевременной оптимизации, но упрощение не должно нарушать бизнес-инварианты.
- Ошибки и отказные сценарии являются частью дизайна, а не исключением из него.

## 2. TDD как обязательный процесс

Каждая функциональность разрабатывается циклом:

```text
Red    -> написать падающий тест на требование
Green  -> реализовать минимальное решение
Refactor -> улучшить код, не меняя поведения
Docs   -> обновить документацию и примеры
```

Код без соответствующего теста не считается завершённым. Тесты пишутся до реализации для:

- успешных сценариев;
- невалидных входных данных;
- граничных значений и точности денег;
- повторов и дубликатов команд;
- конкурентных и конфликтующих действий;
- частичного исполнения;
- отказов зависимостей;
- восстановления и replay;
- изменений версии схемы;
- безопасности и контроля доступа.

## 3. Обязательные уровни тестирования

| Уровень        | Область                                        | Требование                                |
| -------------- | ---------------------------------------------- | ----------------------------------------- |
| Unit           | value objects, policies, matching engine       | каждый branch и инвариант                 |
| Property-based | order book, price-time priority, money, ledger | генерация широкого набора комбинаций      |
| Contract       | commands/events, REST, WebSocket               | совместимость producer/consumer и API     |
| Integration    | PostgreSQL, Redpanda, snapshots, projections   | реальные контейнеры через Testcontainers  |
| E2E            | пользовательские бизнес-потоки                 | полный сценарий от команды до read-модели |
| Failure        | retry, duplicate, timeout, crash, replay       | проверка безопасного восстановления       |
| Load           | order flow, market data fan-out, recovery      | проверка p50/p95/p99 и lag                |
| Security       | auth, roles, rate limits, isolation            | позитивные и негативные сценарии          |

Покрытие строк само по себе недостаточно. Критерий качества — покрытие требований, состояний, переходов и отказов. Для финансового ядра должны быть тесты инвариантов, например: баланс не создаётся из воздуха, встречные заявки исполняются корректно, повтор команды не создаёт вторую операцию.

## 4. Структура модулей

Каждый модуль обязан иметь:

```text
module-name/
├── README.md              # назначение, границы, публичный контракт
├── docs/
│   ├── invariants.md      # правила и инварианты
│   ├── flows.md           # основные sequence/flow diagrams
│   └── decisions.md       # локальные решения и trade-offs
├── src/
├── test/                  # unit/property/contract tests
└── test-fixtures/         # только переиспользуемые фикстуры
```

Для небольшого модуля допускается один `README.md` вместо вложенной папки `docs/`, если в нём сохранены все обязательные разделы.

Документация модуля должна отвечать на вопросы:

- какую задачу решает модуль;
- за что он отвечает и за что не отвечает;
- какие входные команды и выходные события имеет;
- какие инварианты гарантирует;
- какие зависимости допускаются;
- как обрабатывает ошибки, retry и дубликаты;
- как его запустить и протестировать;
- какие решения были приняты и почему.

## 5. Глобальная документация

Папка `docs/` содержит документацию, общую для системы:

- `system-design-requirements.md` — требования и бизнес-правила;
- `architecture.md` — компоненты, потоки и хранение;
- `technology-stack.md` — технологические решения;
- `project-standards.md` — этот документ;
- `adr/` — архитектурные решения;
- `runbooks/` — эксплуатационные процедуры;
- `api/` — публичные API-контракты;
- `events/` — глобальные схемы commands/events;
- `testing/` — стратегии и сценарии тестирования.

Каждый документ имеет статус (`draft`, `accepted`, `deprecated`) и дату последнего изменения.

## 6. Архитектурные решения (ADR)

Значимые решения оформляются отдельным файлом `docs/adr/NNNN-title.md`:

```markdown
# ADR NNNN: Название решения

Статус: proposed | accepted | deprecated
Дата: YYYY-MM-DD

## Контекст

## Решение

## Рассмотренные альтернативы

## Обоснование и trade-offs

## Последствия

## Тесты и критерии проверки
```

Нельзя менять принятое решение молча. Если контекст изменился, создаётся новый ADR, который явно заменяет старый.

## 7. Правила событий и контрактов

- Каждое событие имеет уникальный `message_id`, `message_type`, `message_version`, `sequence`, `correlation_id`, `causation_id` и `occurred_at`.
- События описывают факт, команды — намерение.
- Публичные и внутренние контракты версионируются.
- Breaking change требует нового типа/версии, миграции и теста совместимости.
- Событие должно содержать все данные, необходимые consumer-у для обработки критичного факта.
- Consumer обязан быть идемпотентным и поддерживать повторную доставку.
- Изменение схемы сопровождается обновлением `docs/events/` и contract tests.

## 8. Код и стиль

- TypeScript в strict mode.
- Запрещены `any` без локального обоснования и теста.
- Денежные значения не используют floating point.
- Время передаётся через абстракцию clock; production-код не вызывает системные часы напрямую в доменной логике.
- Идентификаторы доменных объектов типизируются и не смешиваются со строками без необходимости.
- Controller принимает/возвращает DTO; доменная модель не публикуется напрямую наружу.
- NestJS-модули являются адаптерами и composition root, а не местом размещения бизнес-правил.
- Любая ошибка имеет определённый тип, код и ожидаемую стратегию retry/отказа.
- Публичные классы, функции, методы, типы и интеграционные границы сопровождаются JSDoc-комментариями на русском языке. Комментарий объясняет назначение и существенное поведение кода, а не пересказывает имя метода.

## 9. Definition of Done

Задача считается завершённой только если:

- требования и сценарии записаны;
- код реализован через TDD;
- unit, integration и необходимые contract/e2e/failure tests проходят;
- проверены позитивные, негативные, граничные и повторные сценарии;
- обновлена локальная документация модуля;
- обновлена глобальная документация или ADR, если изменена архитектура;
- добавлены metrics, logs и correlation IDs для нового потока;
- миграции и rollback/recovery-план проверены;
- CI выполняет форматирование, lint, typecheck, тесты и сборку;
- нет известных нарушений инвариантов или необъяснённых flaky-тестов.

## 10. Проверки CI

Каждый pull request должен запускать:

1. форматирование и lint;
2. TypeScript typecheck;
3. unit и property-based tests;
4. integration tests с контейнерами;
5. contract tests;
6. сборку всех приложений;
7. проверку документации и схем событий;
8. отчёт о покрытии требований и тестов.

Невыполненный обязательный тест блокирует merge. Исключение допускается только с временным ADR или issue с ответственным и сроком устранения.

## 11. Локальный запуск и gate этапа 0

Требуется Node.js версии из `engines` и pnpm версии из `packageManager` в корневом `package.json`. Из чистого checkout выполняются:

```bash
pnpm install --frozen-lockfile
pnpm security:check
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

Для разработки backend запускается командой `pnpm dev`, после чего liveness проверяется запросом `curl http://localhost:5000/health`. Сборочные артефакты, coverage и файлы окружения игнорируются Git и дополнительно запрещены проверкой `pnpm security:check` в tracked-файлах. Межмодульные контракты импортируются только через публичный entrypoint пакета; импорты во внутренние `src` другого пакета запрещены.

Definition of Done этапа 0 выполнен, когда все команды выше проходят на чистом checkout, smoke E2E проверяет `/health`, CI запускает тот же набор проверок, а документация и ADR conventions доступны в репозитории.

## 12. Конфигурация окружений

Для разработки используется `.env.development`, для production — `.env.production`. Docker Compose-файлы `docker-compose.development.yml` и `docker-compose.production.yml` являются воспроизводимыми точками входа и запускаются командами `pnpm docker:development` и `pnpm docker:production` соответственно.

В NestJS используется `@nestjs/config` через глобальный `ConfigModule`. Обязательные параметры читаются только через `ConfigService.getOrThrow<T>()`. `ConfigService.get<T>(key, fallback)` допускается только для параметров с безопасным и документированным значением по умолчанию, например `PORT` и `HOST`. Секреты не коммитятся в env-файлы и передаются deployment-средой.
