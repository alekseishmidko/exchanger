# Health module

## Назначение

Предоставляет безопасные liveness/readiness endpoints backend-приложения. Модуль не содержит бизнес-логики и не раскрывает тексты ошибок инфраструктуры.

## Контракт

### Liveness

`GET /health/live` (также `GET /health` для обратной совместимости)

Ответ `200`:

```json
{
  "status": "ok"
}
```

Liveness отвечает `200`, если HTTP-процесс способен обслуживать запросы. Он не вызывает базу данных, брокер или другие внешние зависимости.

### Readiness

`GET /health/ready`

При готовности:

```json
{
  "status": "ok",
  "checks": {}
}
```

При отказе критичной зависимости возвращается `503` и безопасный статус `unavailable`. Технические сообщения исключений, connection strings и секреты в ответ не попадают.

Критичные зависимости подключаются через `HEALTH_DEPENDENCIES`; каждая предоставляет имя и асинхронный `check()`. Отсутствие зарегистрированных зависимостей означает готовность текущего минимального приложения, но не заменяет readiness checks будущей инфраструктуры.

## Correlation ID и logging

Каждый HTTP-запрос получает `x-correlation-id`. Переданный идентификатор ограничивается 128 символами, а при его отсутствии генерируется UUID. Идентификатор возвращается в response header и попадает в structured log вместе только с method, URL и status code. Payload, headers и секреты не логируются.

## Правила

- Liveness не зависит от инфраструктуры.
- Readiness отражает отказ критичной зависимости и не маскирует его кодом `200`.
- Конфигурация валидируется при старте приложения; некорректный `NODE_ENV`, `PORT` или отсутствующий `SERVICE_NAME` блокируют запуск.
- Обязательные настройки читаются через `ConfigService.getOrThrow`, параметры с fallback — через `get`.
- Тесты liveness/readiness и отсутствие секретов в ответах/log fields обязательны.
